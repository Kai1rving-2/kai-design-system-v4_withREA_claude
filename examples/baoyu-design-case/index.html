DESIGN METHOD / LEARNING PRACTICE

让 AI 以设计师的方式
工作，而不只是写网页。

baoyu-design 是一套给本地 AI agent 使用的设计 Skill / 工作流。它让设计从理解需求、寻找真实视觉语境开始，经过探索和可交互原型，再沉淀为可以反复使用的视觉系统。

先看课件学习 →查看安装方法 ↗
不是一个新模型不只是生成 HTML一次设计，可以成为下一次的起点
01 / UNDERSTAND

先弄清：它是什么？

它将设计方法、工具适配和现成脚手架组合成一个 Agent Skill。模型仍然由你使用的 Codex、Claude Code 或 Cursor 环境提供；Skill 为 agent 提供做设计的流程与标准，而不是替换模型。来源 ↗

一句话辨别

普通指令容易直奔“给我一个页面”；设计工作流会先问“给谁看、要理解什么、沿用什么视觉语言”，再决定页面该怎样组织。

两种工作方式的对照；右侧描述的是工作流提供的支持，并非每次调用都会自动完成所有步骤。
观察维度普通“AI 写网页”baoyu-design 驱动的工作流
设计理解常常直接实现一句需求先确认受众、约束和视觉参考
方案探索通常交付单一答案可以对布局、交互或视觉方向做多方案探索
交互原型可能停在静态排版按任务选择可操作的 HTML 原型
Design System样式容易在不同页面间漂移可创建、绑定并复用 tokens / 组件 / 起始页
长期维护代码可保留，但规范往往靠记忆输出留在项目里，可持续迭代与同步视觉约束
复杂内容容易变成连续段落可选图解、交互和分层阅读结构

请注意：以上是“工作方法对比”，不是对所有普通 prompt 的绝对判断；有经验的设计师也能用精心写的普通 prompt 实现类似流程。

02 / SET UP

安装，然后让 agent 读到它

以下命令来自项目的官方 README；需要 Node.js 来运行 npx。安装器会将 Skill 文件放到相应 agent 的 skills 目录；它不是网页运行时依赖。官方说明 ↗

01

选择范围：项目内 or 全局

只想在当前项目试用、便于团队一同管理时选项目内；希望多个项目都能调用时选全局。在目标项目的终端执行：

安装 / Codex
# 仅当前项目（明确指定 Codex）
npx skills add JimLiu/baoyu-design --agent codex

# 所有项目（全局）
npx skills add JimLiu/baoyu-design -g --agent codex

Claude Code 或 Cursor 可将 codex 分别替换为 claude-code / cursor；也可省略 --agent 交给 CLI 检测。项目内通常位于 .agents/skills/（Codex / Cursor）或 .claude/skills/（Claude Code），全局则位于用户目录对应位置；以安装器输出为准。

02

验证与调用

先用 --list 查看可安装的 Skill；安装完成后检查对应 skills 目录是否包含 baoyu-design/SKILL.md，新开 agent 会话，再在任务里显式指定：

验证 / 调用示例
npx skills add JimLiu/baoyu-design --list

# Codex prompt（Skill 已被当前环境识别时）
请用 $baoyu-design，为我的课程讲义设计一个可交互的学习 HTML。
先梳理知识点与来源页码，再探索内容结构，最后验证页面。

# Claude Code：可在输入框使用 /baoyu-design

验证“可调用”不只看目录：还应确认 agent 新会话能识别 Skill，并能按它的流程输出设计。不同 agent 的显式触发语法并不完全相同。

03

之后怎样更新？

更新 / 按安装范围
# 当前项目
npx skills update baoyu-design -p -y

# 全局安装
npx skills update baoyu-design -g -y

更新后重启 agent 或重新开启会话，让新版本文件被重新载入；如需保守升级，先查看更新内容。

03 / THE ENGINE

它是怎样工作的？

把它看成「入口 → 方法 → 专项工具 → 可复用产物」比把它看成一句万能提示词更准确。下图是依据官方项目结构绘制的教学抽象，而非每个任务的强制执行顺序。结构依据 ↗

入口与核心

SKILL.md 负责让 agent 识别任务、加载适当文件；system-prompt.md 规定设计过程与质量要求。它们提供方法，不会自行理解你的课件或运行一个新模型。

专项与产物

built-in-skills/ 将交互原型、幻灯片、图解、设计系统创建与使用等任务拆开；starter-components/ 提供可复用的界面脚手架。视觉系统可在探索后沉淀，再约束之后的页面。

04 / CHOOSE WELL

适合做什么，不必做什么

不是每个任务都要启动完整设计流程。先问：内容有多复杂？读者需要操作吗？这套视觉会不会持续使用？

01 / INTERFACE

UI / 页面设计

适合：有品牌语境、信息层级或多种布局要权衡。
不太适合：只调整一个按钮的文案。

02 / PROTOTYPE

交互原型

适合：验证操作路径、状态和反馈。
不太适合：把 HTML 原型当成未经测试的正式产品。

03 / SYSTEM

个人 Design System

适合：多个项目需要同一种字体、颜色、组件和语气。
不太适合：只会用一次的单页海报。

04 / PRESENT

Slides / 信息展示

适合：用节奏与图解讲清复杂概念。
不太适合：需要直接替代严谨的论文或原始讲义。

05 / READ

内容型学习页面

适合：需要概念分层、比较、练习和复习路径。
不太适合：原文仅一段、没有可解释结构的摘要。

06 / EVOLVE

已有视觉的沉淀

适合：已有代码、UI kit 或风格规范，想持续复用。
不太适合：没有审核就让 AI 擅自定义品牌。

简单静态 HTML 就够时：一页摘要、一个列表、几张知识卡片，只要阅读顺畅就先做轻。需要反复迭代的长期项目，再投入系统化的组件和视觉约束。
05 / LOCAL PRACTICE

设计方法，与我自己的 KAI v4

这份仓库已沉淀 KAI v4 的字体、色彩、组件、交互状态与示例；它是可以直接使用的个人视觉语言。baoyu-design 则更像探索和生产视觉语言时的设计方法与 agent 工作流。KAI v4 指南 ↗

EXPLORE / CREATE

baoyu-design

协助提问、比较方向、做原型；需要时帮助把决定整理为 Design System。

↔
REUSE / REFINE

KAI v4

已沉淀的 Quiet Base + Signature；新页面优先沿用现成的视觉和交互规范。

关于“当初如何创作 v4”：现有仓库记录的是 v4 从 v3 做减法、形成规范的过程；这里仅用“方法辅助探索、系统负责稳定输出”概括两者关系，不虚构具体历史步骤或把 KAI v4 说成某个工具自动生成的结果。

06 / LEARNING HTML · FOCUS

把一份课件，变成一页能学的 HTML

目标不是把 PDF 换一种排版，而是让概念有入口、难点能观察、结论能复习。设计 Skill 负责如何表达和组织；课件理解、事实核对和教学逻辑仍需要单独完成。

页面可以包含
  • 概念讲解：先定义，再举例，再指出常见误解。
  • 分步可视化：把抽象过程拆成可以暂停观察的步骤。
  • 知识卡片与对比表格：帮助建立差异与联系。
  • 小测试与重要结论：检查理解，方便回看。
  • 原课件页码：对每个关键结论标注真实出处。
不要省略的核对

先读取 PDF 中的正文、图表与公式，确认页码；再检查概念与推导是否忠于讲义，必要时查教材或原文。Skill 不会自动保证知识正确，更不能替代授课者的判断。互动题必须给出正确答案的理由，而不只是“答对了”。

推荐工作流：按难度逐级加深

LIGHT / 轻简单课件总结

提取大纲 → 核对页码 → 静态标题、列表与结论。一个清楚的 HTML 即可。

MEDIUM / 中中等复杂度学习 HTML

画出概念关系 → 设计分步图解 → 加一两道可解释的自测 → 让同学试读。

DEEP / 深复杂交互式学习项目

先定义学习目标与状态 → 做原型与测试 → 复用组件和 KAI v4 → 验证内容、无障碍与移动端。

与未来 learning-html 的衔接：本仓库的 learning-html 示例 ↗ 已展示“观察 → 操作 → 自测”的轻量结构。未来可以让 baoyu-design 帮忙探索知识的呈现方式，同时让 KAI v4 固定视觉和交互规范；这是一条可尝试的工作流，不是已经完成的自动化管线。
07 / TRY IT

复制一个 Prompt，开始第一版

每个示例都要求先读材料、保留来源并验证输出。使用 Codex 且 Skill 已识别时，保留 $baoyu-design；其他 agent 请按自己的 Skill 调用方式替换。

01 / 一份课件，一个可复习页面

学习型 HTML 页面

请使用 $baoyu-design，将我提供的课件 PDF 制作成一个中文学习型 HTML 页面。
先提取章节、概念、公式和例题，列出对应的原课件页码；不确定的地方先标出待核对。
面向第一次学习这门课的人，组织为：导读 → 概念解释 → 分步图解 → 对比表 → 2 道有解释的自测 → 结论。
沿用本仓库的 KAI Design System v4；使用原生 HTML/CSS/JS，保持移动端可读；完成后请检查事实、交互和页码引用。
02 / 找到个人学习页面的审美

探索视觉方向

请使用 $baoyu-design，阅读当前仓库的 SKILL.md、readme.md、styles.css 与 learning-html 示例。
基于 KAI v4 探索 2 种学习页面的信息组织方式：一种适合速读复习，一种适合循序渐进理解。
保持 KAI 的安静基底、克制的蓝色和清晰的交互状态；对每种方案说明适合的课程材料、取舍及未来可复用的组件。
先给出结构和比较，再实现我选择的一种，不要修改设计系统的生成文件。
03 / 一门课，逐步解释的交互

Explainable HTML

请使用 $baoyu-design，为我上传的课程讲义设计一个可解释的交互式学习 HTML。
先从讲义中选择一个值得交互演示的核心概念，核对定义、步骤与来源页码，并写明学习目标。
设计“先预测 → 动手操作 → 看到过程 → 解释原因 → 自测反馈”的路径；图解使用 HTML/CSS 或 SVG，不用截图代替解释。
样式沿用 KAI v4，支持键盘与手机；将页面放在独立的 examples 子目录，并列出仍需人工核对的内容。
08 / BE HONEST

它的价值，也有边界

有帮助的地方

  • 把设计理解、探索、原型验证串成流程。
  • 能将视觉决定沉淀为 Design System。
  • 适合需要反复迭代与多人复用的项目。
  • 有助于让复杂内容变得可阅读、可操作。

依然需要你判断

  • 不能自动保证课件内容、页码或公式准确。
  • 简单任务使用完整流程可能得不偿失。
  • 复杂教学项目仍要人工审稿与用户测试。
  • 输出质量取决于模型能力、输入材料与审查。
常见问题：装好 Skill 后，是不是每页都必须做 Design System？

不用。创建系统、使用已有系统、做一张静态学习卡，是不同规模的任务。只有当视觉需要跨多个页面长期复用时，才值得建立完整系统；单次任务从清晰的 HTML 开始即可。

09 / START HERE

先拿一份课件，做一个概念。

baoyu-design 的核心价值不是替你“生成得更漂亮”，而是让设计过程可讨论、可验证、可复用。对我与朋友来说，它提供一种把讲义转成可理解、可练习页面的方法；KAI v4 则让这些页面有稳定的视觉归属。

  1. 选一份有明确来源页码的课件，只挑一个概念。
  2. 先人工核对定义与例题，再使用上方 Prompt 制作第一版。
  3. 请一位朋友试学：哪里看不懂，就从那里修改。
